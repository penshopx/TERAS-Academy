# REPLIT — POST-MERGE HARDENING & SCHEMA RECONCILIATION

Lanjutkan pekerjaan dari kondisi saat ini.

JANGAN menambahkan fitur baru terlebih dahulu.

Prioritas sekarang adalah memastikan hasil merge Path B tetap stabil dan seluruh workflow Task #1 serta safety hardening tetap berjalan.

## 1. REKONSILIASI DATABASE

Akar masalah yang ditemukan:

Kode menggunakan:

`teras_people.email`

tetapi database aktif belum memiliki kolom tersebut.

Lakukan rekonsiliasi schema secara aman.

Pastikan:

* schema source of truth jelas
* database schema sesuai dengan Drizzle schema
* kolom `teras_people.email` tersedia jika memang merupakan bagian dari model yang sekarang digunakan
* migration/schema push dapat dijalankan non-interaktif
* tidak ada destructive migration tanpa alasan
* data existing tidak hilang
* unique constraint email ditangani dengan aman

Jangan menggunakan workaround yang hanya membuat smoke test lewat.

Perbaiki akar masalah schema drift.

---

# 2. PERBAIKI POST-MERGE SETUP

Script post-merge sebelumnya menggunakan filter package yang salah:

`db`

sehingga migrasi tidak berjalan.

Perbaiki script tersebut.

Post-merge setup harus secara deterministik melakukan:

1. install/build dependencies jika diperlukan
2. database schema reconciliation
3. seed idempotent
4. validation
5. smoke test

Jangan bergantung pada stdin interaktif.

---

# 3. NON-INTERACTIVE DATABASE SETUP

Drizzle sebelumnya meminta konfirmasi untuk unique constraint email.

Post-merge process tidak boleh berhenti karena prompt interaktif.

Gunakan mekanisme migration/schema deployment yang aman dan non-interaktif.

Jika diperlukan:

* buat migration eksplisit
* review SQL migration
* gunakan migration runner
* pastikan migration dapat dijalankan berulang tanpa merusak database

Jangan mengotomatisasi dengan `--force` atau destructive option sebelum memahami dampaknya.

---

# 4. SEED HARUS IDEMPOTENT

Pastikan seed tidak membuat duplicate data setiap kali dijalankan.

Seed harus dapat dijalankan:

* setelah migration
* setelah merge
* setelah deployment
* setelah database reset

tanpa menghasilkan duplicate records yang merusak foreign key atau workflow.

Gunakan upsert / deterministic IDs jika sesuai dengan architecture.

---

Jangan hanya memeriksa migration file.

Periksa juga actual database schema.
