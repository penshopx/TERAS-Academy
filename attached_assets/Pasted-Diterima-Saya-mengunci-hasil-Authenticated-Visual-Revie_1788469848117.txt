# Prinsip arsitektur UI yang sekarang menjadi acuan

### 1. Satu kondisi learner, banyak perspektif role

Bukan:

> Learner state
> Trainer state
> Assessor state

seolah-olah tiga state berbeda.

Tetapi:

> **Satu canonical learner state → dipresentasikan berbeda sesuai kewenangan role.**

Sehingga alurnya harus konsisten:

**Learning → Practice → Evidence → Trainer Review → Assessment → Safety Enforcement → Gap/Remediation → Readiness → Capability Passport**

---

# 2. Hierarki informasi baru

Setiap halaman authenticated idealnya menjawab pertanyaan sesuai role.

### Learner

> **Apa yang harus saya lakukan sekarang?**

### Trainer

> **Siapa yang perlu saya bantu, apa masalahnya, dan apa tindakan saya?**

### Assessor

> **Assessment mana yang membutuhkan keputusan, berdasarkan evidence dan criteria apa, dan apa dampaknya?**

### Readiness

> **Mengapa learner belum/ sudah ready?**

### Passport

> **Apa yang benar-benar sudah terbukti dari perjalanan capability learner?**

Ini membuat lima halaman tersebut menjadi **satu sistem**, bukan lima dashboard terpisah.

---

# 3. Safety menjadi state transversal

Safety tidak boleh hanya hidup di Assessment atau Readiness.

State safety harus dapat dikenali ketika relevan pada:

**Learner → Trainer → Assessor → Readiness → Passport**

Dengan prioritas:

> 🟢 **Safety Cleared**
> 🟡 **Safety Not Attempted**
> 🔴 **Critical Safety Failure**

Dan prinsip yang sudah dikunci:

> **Safety failure cannot be hidden by an average score.**

---

# 4. Evidence harus memiliki traceability

Evidence bukan sekadar angka:

> `1 evidence`

Tetapi harus dapat ditelusuri:

**Criteria → Evidence → Validation → Assessment → Decision → Gate → Readiness**

Ini juga menjadi penghubung utama antara Trainer dan Assessor.

---

# 5. Assessment harus menjadi decision-support cockpit

Assessor tidak boleh hanya melihat:

> `M07 Practical Assessment — DECISION`

Tetapi harus dapat memahami:

> **Candidate → Criteria → Evidence → Rubric → Safety → Requested Decision → Stored Decision → Impact → History**

Dan bila ada perbedaan:

> **Requested Decision:** Competent
> **Stored Decision:** Not Competent
> **Reason:** Critical safety criterion not met

**Stored decision adalah official state.**

---

# 6. Ownership harus eksplisit

Setiap actionable state idealnya mempunyai:

> **Current status → Owner → Next action**

Contoh:

**Evidence pending validation**

> Status: Menunggu Validasi
> Owner: Trainer
> Action: Tinjau Evidence

Setelah ditolak:

> Status: Perlu Perbaikan
> Owner: Learner
> Action: Kirim ulang Evidence

Setelah assessment:

> Status: Menunggu Remediation
> Owner: Learner + Trainer

Dengan ini queue berubah dari sekadar daftar menjadi **operational workflow**.

---

# 7. Responsive shell menjadi pekerjaan pertama

Ini sebaiknya menjadi **Hardening Sprint #1**.

Bukan memperbaiki lima halaman satu per satu secara terpisah, tetapi membuat satu pola:

### Desktop

```text
Sidebar │ Main Content
```

### Tablet

```text
[☰] │ Main Content
```

### Mobile

```text
[☰] TERAS
────────────
Main Content
```

Dengan aturan:

* tidak ada horizontal clipping;
* CTA selalu utuh;
* table berubah menjadi card bila diperlukan;
* sidebar menjadi drawer;
* satu pola scroll;
* content menggunakan full available width.

Setelah shell selesai, lima halaman bisa mengikuti pola yang sama.
